# M0036 — Sprint 3.6: Audit Orchestrator

> Status: **Complete** (2026-07-14) · Branch: `feature/audit-findings-engine`
> Workflow only: the orchestrator coordinates OCR/review/CRM/matching/report —
> it never performs them. Mock stage executors; human review genuinely waits.

## What Shipped

- **`services/orchestrator/`** — `AuditOrchestrator` (job lifecycle, transition
  validation, retry, cancellation, progress), `AuditStateMachine`
  (`state-machine.ts`, 7 statuses, illegal transitions rejected),
  `AUDIT_PIPELINE` (OCR → HUMAN_REVIEW → CRM_RETRIEVAL → MATCHING → REPORT),
  pluggable `StageExecutor` contract + mock executors, `AuditProgress`
  computation (percentage, elapsed, estimated remaining from measured stage
  durations).
- **Persistence**: `AuditJob` + `AuditJobStage` (migration
  `20260713165731_audit_orchestration`) — attempts, errors, waiting reasons,
  timestamps. Recovery derives from rows; concurrent transitions are rejected
  by status-guarded updates.
- **Seam realized (ADR-029)**: `getAuditService()` returns the orchestrator;
  the M1.1 promise is kept with zero caller churn. Submission statuses now
  advance mechanically through the DOMAIN_MODEL §5.1 machine as stages run,
  ending in `COMPLETED`.
- **Events**: `audit.started`, `audit.stage.started/completed/failed`,
  `audit.cancelled` added to the catalog; existing `audit.completed/failed`
  now actually fire.
- **UI**: `/audit/[id]/progress` — status + progress bar, five-stage timeline
  with per-stage status icons/attempts/timestamps/errors, and controls
  (start / mark review complete / retry / cancel / start new run), polling
  while active. "Simulated pipeline" banner (PROJECT_RULES 28). Reached via a
  Progress button on submission views (`audit:manage` to operate).

## Notes

- Runs execute inline in the request (mock stages are sub-second). Real OCR
