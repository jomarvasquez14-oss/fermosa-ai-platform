# M0037 — Sprint 3.7: Rule Engine

> Status: **Complete** (2026-07-14) · Branch: `feature/audit-findings-engine`
> Deterministic business rules — NOT AI. Consumes confirmed OCR + normalized
> CRM; produces canonical AuditFindings. First real stage executor wired in.

## What Shipped

- **`services/rules/`** (ADR-030): `Rule` / `RuleContext` / `RuleResult`
  (pass · warning · fail · review-required) / `RuleRegistry` (pluggable,
  duplicate-id-safe) / `RuleEngine` evaluator + **thirteen built-in rules**:
  patient name, treatment, therapist, invoice integrity, payment sums,
  branch, date, duplicate-patient (ambiguity → review-required), deleted
  treatment (CRITICAL), edited treatment, missing CRM record
  (unmatched patient / missing-in-CRM CRITICAL), missing invoice, duplicate
  entry. Pure and synchronous; adding a rule = one object + one registration.
- **Configuration as data**: similarity threshold, time tolerance, severity
  weights, per-rule enable/weight overrides (`DEFAULT_RULE_CONFIG`).
- **Scoring**: weighted risk score (capped 100), submission score
  (100 − risk), `branchScore` aggregation — the dashboard KPI primitives.
- **`lib/findings.ts`**: finding domain vocabulary relocated from the UI kit
  (layering: services depend on lib, never components); kit re-exports.
- **`findingService`** — the ADR-028 persistence layer, arriving with the
  first real producer: evidence validated at the write boundary, §5.5
  transitions with timestamps + resolution notes, branch scoping, idempotent
  per (submission, source) since findings are never deleted.
- **First real executor**: the orchestrator's MATCHING stage now runs the
  rule engine — simulated confirmed-OCR (deterministic mock provider) +
  CRM records via the connector seam — and persists findings. `/findings` is
  DB-backed; status changes persist (server action, `audit:manage`).

## Verification

- **25 new tests** (suite: **139 green**): one per rule (13), combination
  ("rotten submission" fires many rules at once), config
  (disable/re-weight/threshold), score capping + branch aggregation,
  similarity behavior, **performance: 1,000 entries × 40 patients in
  < 300 ms**, and DB-backed finding-service integration (idempotency,
  evidence rejection, branch scoping, workflow with timestamps, out-of-scope
  denial).
- Browser-verified: fresh audit run → matching produced **12 persisted
  findings** (deleted-record CRITICAL among them) → `/findings` renders them →
  "Mark reviewed" **survives a page reload** (persisted workflow).
- Gates: typecheck / lint / build clean.

## Known Limitation

Re-running matching does not refresh existing findings (idempotency guard —
deletion is forbidden). A versioned re-evaluation strategy is future work,
noted in ADR-030.
