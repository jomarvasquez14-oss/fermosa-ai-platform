## The 10 new rules (`services/rules/rules-extended.ts`)

| id | logic | category | severity |
| --- | --- | --- | --- |
| `invoice-after-treatment` | invoice dated before the treatment it bills | MISMATCHED_FIELD | MEDIUM |
| `invoice-without-treatment` | invoice whose service matches no treatment (mirror of `missing-invoice`) | MISSING_IN_LOGBOOK | MEDIUM |
| `duplicate-invoice` | invoices sharing a refNo or (service, amount, date) | DUPLICATE_ENTRY | MEDIUM |
| `duplicate-treatment` | CRM treatments sharing (procedure, date, branch) | DUPLICATE_ENTRY | LOW |
| `impossible-session-sequence` | package sessionNumber not increasing along the date order | MISMATCHED_FIELD | MEDIUM |
| `impossible-package-progression` | one package shows different sessionsTotal values | RECORD_EDITED | MEDIUM |
| `repeated-edits` | ≥ `repeatedEditsThreshold` (default 3) "updated" activity events | RECORD_EDITED | HIGH |
| `suspicious-activity-frequency` | > `activityFrequencyThreshold` (default 10) activity events | OTHER | MEDIUM |
| `staff-mismatch` | one package's sessions attributed to different staff | MISMATCHED_FIELD | LOW |
| `package-over-completion` | sessionNumber > sessionsTotal | MISMATCHED_FIELD | HIGH |

Two additive config fields (`repeatedEditsThreshold`, `activityFrequencyThreshold`) in
`RuleEngineConfig`/`DEFAULT_RULE_CONFIG`; `EXTENDED_RULES` registered in
`createRuleEngine`. All 10 map to existing enum values → no migration, no ADR.

## The 5 requested rules deliberately NOT built (reused instead)

Per the project owner's "no duplicate rules" directive, these map to existing logic and
were skipped (documented, not implemented):

| Requested | Reused / reason |
| --- | --- |
| `treatment-without-invoice` | existing **`missing-invoice`** (same-day treatment lacking an invoice) |
| `deleted-treatment` | existing **`deleted-treatment`** |
| `edited-treatment` | existing **`edited-treatment`** (sensitive-field edits). The new `repeated-edits` is distinct — it flags edit *frequency*, not any single edit. |
| `invoice-balance-mismatch` | existing **`invoice`** rule (checks `amount = paid + balance`) |
| `branch-mismatch` (treatment vs invoice branch) | **not implementable** — `invoices[]` carries no branch field in `NormalizedCrmPatientRecord`. The existing **`branch`** rule already checks treatment branch vs the submission branch. |

## Distinctness (verified in review)

The reviewer confirmed each new rule is genuinely distinct: `repeated-edits` counts all
"updated" events regardless of field (orthogonal to `edited-treatment`'s sensitive-field
check); `duplicate-treatment` operates on CRM records while `duplicate-entry` operates on
logbook lines; `invoice-without-treatment` is the true opposite-direction mirror of
`missing-invoice`.
