## Verification method: capture-replay harness

`docs/crm-reference/verify-captures.mts` (local-only, reusable) drives the REAL
`PlaywrightBrowserDriver` in headless Chromium against **file:// copies of the
captures** and executes the actual page objects and parsers on them — the strongest
verification possible without credentials. The replay is strictly offline (absolute
asset URLs neutralized first; the first run inadvertently fetched static CSS/JS from
the live site — no auth, no data sent — and the harness now prevents that).
**Final result: 27/27 PASS**, including 50 patient rows parsed with cid extraction,
5 treatment packages / 12 session rows with ISO dates, 10 activity entries with
nested old/new diff tables, and announcement neutralization (removed=2, idempotent).

## Three real bugs the replay caught (none visible to mocks)

1. **Hidden-input cell corruption** — the treatment DATE cell contains a hidden
   `treatment_record_id` input BEFORE the date input; the cell extractor took the
   first control, so every real date would have parsed as a record id →
   `LayoutChangedError` on live. Fixed: `input:not([type=hidden])`.
2. **Fingerprint race** — the CRM ships server HTML with tables CSS-hidden until page
   JS initializes them; the instant `isVisible` fingerprint would have misreported
   healthy live pages as CRM_LAYOUT. Fixed: `assertFingerprint` now WAITS (10s) for
   visibility. Robustness increased, never reduced.
3. **select2 blindness** — the activity filter selects are select2-enhanced: the
   native `<select>` is permanently `display:none` on live, so it can never be a
   fingerprint. Swapped for a plain input.

## Announcement handling is now read-only-correct (ADR-036)

The real modal lifecycle (from `announcements.js` + both dashboard captures):
`#instant-announcement-modal` re-polled every **5 seconds** on every authenticated
page, static backdrop, close button disabled until "I have read the announcement. Do
not show again" is ticked + a 5s countdown, and closing **POSTs mark-as-read** (staff
read-tracking; the checklist variant records completed-by). Automation therefore
**neutralizes** the modals — client-side node removal (also defeats the 5s re-poll),
no network call, announcement stays unread for humans — after login AND after every
navigation. The mark-as-read controls are `neverInteract`.

## Capability decision

**`invoiceDetail` stays `false`.** No recording and no capture shows the detail view
or its trigger; enabling it would be guesswork. Payments remain `null` (schema-legal).
What would flip it: a Codegen recording of one invoice-row click, or a
Complete-save of the profile page with the invoice tab open + one detail view
(`docs/crm-reference/CODEGEN_GUIDE.md`).
