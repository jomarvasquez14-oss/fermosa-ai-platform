# M0034 — Sprint 3.4: Mock CRM Connector

> Status: **Complete** (2026-07-13) · Branch: `sprint-2a-upload-batch`
> First implementation on the CRM seam — fixtures only; the live CRM is never
> touched. No browser automation, no Playwright connector, no OCR/AI changes.

## What Shipped

- **Contract realized**: `CRMConnector` now IS the ADR-027 three-method contract —
  `healthCheck` / `findPatients` / `fetchPatientRecord` — replacing the M1.1
  placeholder shape (pre-freeze refinement, ADR-015). `NormalizedCrmPatientRecord`
  from CRM_DISCOVERY §3 exists in code as a **Zod schema**
  (`services/crm/types.ts`): ISO-string dates, decimal-string money, provenance
  stamped on every record.
- **`MockCRMConnector`** (`services/crm/connectors/mock/`): multi-identifier search
  (name/dob/mobile/email/crmId, formatting-insensitive), outcomes as data
  (`found` / `not-found` / `ambiguous` with candidates — never auto-picked),
  window-filtered retrieval, and every response validated against the schema at
  the boundary before it leaves the connector.
- **Fixture dataset** (`fixtures.ts`, `fixtures/v1`, fully fictional): all eight
  required scenarios — normal patient, multi-session package (GLUTA DRIP ×3/10),
  no treatments, duplicate-name pair (differing dob/mobile), missing invoice,
  empty activity log, **deleted treatment** (visible only via activity diffs),
  **edited treatment** (`amount_paid` / `service.name` old→new) — mirroring the
  real CRM's observed shapes.
- **Simulated infrastructure failures**: reserved names `trigger:unavailable` /
  `trigger:forbidden` / `trigger:layout` throw the typed `AppError`s from
  CRM_DISCOVERY §6, so error paths are exercisable from tests and the dev page.
- **Developer page `/dev/crm`** (Super Admin, `playground:access`, middleware-
  guarded `/dev` prefix): patient search → outcome badge → candidate pick →
  normalized JSON viewer, plus a fixture directory labeled by scenario and the
  documented error triggers. Everything flows through `getCRMConnector()` — the
  page keeps working unchanged when the browser-automation connector lands.
  (Known, deliberate exception: the page imports the fixture _directory listing_
  from the mock module for inspection purposes — dev tooling only.)

## Verification

- **15 new tests** (suite: **96 green**): lookup outcomes incl. ambiguity and
  dob-disambiguation, formatting-insensitive mobile match, error triggers,
  schema validity of _every_ fixture, all eight scenario assertions, window
  filtering, unknown-id NOT_FOUND, health check.
- Browser-verified (Playwright): found→JSON with provenance, ambiguous→2
  candidates→pick, not-found, CRM_UNAVAILABLE error rendering, deleted-treatment
  JSON, Auditor blocked at the route.
- Gates: typecheck / lint / build clean (`/dev/crm` at 6.8 kB).

## What This Unblocks

- **Sprint 4 (matching engine)** develops entirely against the mock — the
  fixture scenarios are precisely the finding classes matching must detect
  (missing invoice, deleted/edited records, never-treated patients).
- **Sprint 3 browser automation** implements the same three methods against the
  live CRM; the acceptance test remains "callers change zero lines".
