# M0063 — CRM Redesign Re-validation (patient-search submit fix)

> Status: **Complete** (2026-07-15) · Branch: `feature/crm-browser-connector`
> The live CRM was redesigned since M0056. Re-validated the whole read-only
> connector against it: the **only** break was the patient-search submit control
> (`<input>` → `<button>`); everything else (profile, treatments, invoices,
> payments, activity, logout, recovery) still reads correctly. The feared
> "profile read is broken" was a **misdiagnosis** — it was date-window filtering.

## What actually drifted

| Area | Finding |
| --- | --- |
| **Patient search submit** | The CRM changed the control from `<input type=submit id=search>` to `<button type=submit id=search>`. The old selector `input[type=submit]#search` matched nothing, so `PatientsPage.search()`'s click auto-waited forever and every CRM search hung. Fixed: `services/browser/selectors/v1.ts` → `button[type=submit]#search`. |
| **Everything else** | No drift. Profile card, tabs, treatment records, invoice DataTable, embedded payment detail (M0056), and activity log all read correctly against the redesigned site. |

## The misdiagnosis (why "0 treatments" was NOT a bug)

An earlier `intake-audit` run reported 0 treatments/invoices for matched patients
and flagged CRITICAL "unrecorded sale" findings. Evidence-first debugging showed
those were **false**: fetching a known-active patient's **full** record through the
connector returns **treatments=22, invoices=10** with full payment detail (cash/bank
mode, `receivedBy`, refNos). The 0s came from the reconciliation **date window**
(`auditDate−7 … auditDate+1`): that patient's real CRM dates were 07-09/07-15, outside
a window built around a 07-04 logbook. Lesson banked for M0065: CRM encoding lags the
logbook date, so the reconciliation window must not be a tight symmetric band. Also
confirmed: **"District" is a real CRM branch** (`Fermosa - District Imus`, branchId 54).

## Changes

- `services/browser/selectors/v1.ts` — patient-search `submit` → `button[type=submit]#search`
  (with a comment recording the live redesign + date observed).
- `services/browser/pages/patients-page.ts` — the search/filter submit + results wait carry
  a 30s `timeoutMs` (`SEARCH_TIMEOUT_MS`), the M0058 pattern: the CRM's server-side search is
  slow and the click auto-waits on that navigation. Defensive hardening, independent of the
  selector fix.
- `services/browser/pages/pages.test.ts` — two regression guards: the search submit selector
  must target a `<button>` (never regress to `input`); the search click must carry a
  navigation-sized `timeoutMs`.
