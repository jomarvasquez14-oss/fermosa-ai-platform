## The seven new rules

1. **repeated-cancellations** (RECORD_EDITED, HIGH) — counts cancel/void/refund
   activity per patient; fires at `repeatedCancellationsThreshold` (default 2).
2. **repeated-deletions** (RECORD_DELETED, CRITICAL) — counts deletion activity;
   fires at `repeatedDeletionsThreshold` (default 2). Deletions destroy evidence.
3. **repeated-invoice-corrections** (RECORD_EDITED, HIGH) — counts invoice/payment
   events with a money-field change (or a bare invoice update); threshold
   `repeatedInvoiceCorrectionsThreshold` (default 2). Distinct from
   `repeated-edits` (which counts *all* updates) by scoping to billing.
4. **large-billing-adjustment** (RECORD_EDITED, HIGH) — scans `activity.changes`
   for a money field whose old→new delta ≥ `largeBillingAdjustmentAmount`
   (default 5000). Grounded in the CRM's own recorded diffs.
5. **unusual-activity-density** (OTHER, MEDIUM) — burst detection: ≥
   `activityBurstThreshold` (default 5) events within a single minute. Distinct
   from `suspicious-activity-frequency`, which counts total volume.
6. **cross-branch-inconsistency** (MISMATCHED_FIELD, MEDIUM) — one package's
   sessions spanning multiple branches, or same-day treatments at different
   branches (a patient can't be in two). Uses `treatment.branch`; distinct from
   `staff-mismatch` (staff per package).
7. **invoice-chronology-anomaly** (MISMATCHED_FIELD, MEDIUM) — invoices sorted by
   numeric reference ordinal must not run counter to their dates; a higher ref
   number with an earlier date signals a backdated correction. Distinct from
   `invoice-after-treatment` (treatment-vs-invoice dating).

## Not implementable against the current schema

None newly — all seven requested-new categories map to available fields
(`activity.changes` money diffs, `activity.logName`/`description` action words,
`treatment.branch`, invoice `refNo`/`dateUpdated`). The M0047 note about
`branch-mismatch` for *invoices* still stands (invoices carry no branch); this
milestone's `cross-branch-inconsistency` works on *treatments*, which do.

## Determinism, config, performance

All rules are pure and synchronous, one `FindingDraft` per non-pass result.
Five additive config fields with defaults (above) — thresholds are data, not
code. **Performance: the full 30-rule engine evaluates 1000 records in < 300 ms**
(asserted test, `rules-extended-2.test.ts` › performance).
