# M0043 — Audit Evidence Snapshot Engine

> Status: **Complete** (2026-07-14) · Branch: `feature/crm-browser-connector` · ADR-035
> Immutable, hash-sealed evidence of what the CRM said at the moment an audit read
> it. The CRM remains the ONLY source of truth — the platform stores evidence, never
> operational copies. No patient table, no treatment table, no synchronization.

## Why this exists

An audit's conclusions are only defensible if the facts they rested on can be
reproduced. The CRM is a live system: treatments get edited, invoices get paid,
records get deleted (that's often the finding!). `AuditEvidenceSnapshot` preserves
"what the CRM looked like at the exact moment the audit executed" so the audit stays
reproducible after the CRM moves on — and so post-audit CRM edits become *visible*
instead of silently rewriting history.

## Data model (one table, one relation)

`AuditEvidenceSnapshot` (`audit_evidence_snapshots`), linked ONLY to
`AuditSubmission` (cascade delete with its aggregate; `crmPatientId` is a provenance
string, deliberately NOT a foreign key — no patient master exists):

| Column                          | Meaning                                                              |
| ------------------------------- | -------------------------------------------------------------------- |
| `record` (jsonb)                | The full `NormalizedCrmPatientRecord` (ADR-027): patient, treatments, invoices + payments, activity log |
| `contentHash`                   | SHA-256 over the canonical (sorted-key) record JSON — integrity seal |
| `connectorKind`                 | Which connector captured it (`mock` / `browser-automation`)          |
| `selectorVersion`               | Retrieval-source version (`crm-selectors/v1`, `fixtures/v1`)         |
| `retrievedAt`                   | The connector's own retrieval timestamp                              |
| `windowFrom` / `windowTo`       | The retrieval window applied, when any                               |
| `snapshotVersion`               | Stored-format version (1) — bump via ADR                             |

Migration: `20260714012212_audit_evidence_snapshots` (applied + verified locally).
Rows are **append-only**: the service exposes no update or delete; immutability is a
service-layer invariant like the audit trail's.

## Snapshot lifecycle

```
Audit submission exists
        │
createSnapshot(submissionId, crmId, window?)
        │ connector.fetchPatientRecord()      ← live read through the seam
        │ validateSnapshotRecord()            ← Zod (ADR-027); malformed evidence rejected, never stored
        │ contentHash()                       ← canonical sorted-key SHA-256
        ▼
   sealed row (append-only)
        │
loadSnapshot(id)                              ← re-validates schema AND hash on every load
        │  ✗ schema → EVIDENCE_INVALID          ✗ hash → EVIDENCE_INTEGRITY   (both loud)
        ▼
compareSnapshotMetadata(snapshot, live)       ← metadata only: evidence hashes, section
                                                counts, provenance. NEVER findings —
                                                interpreting drift is the rule engine's job.
```

**Two hashes, deliberately:** `contentHash` covers the full record including
provenance (tamper detection on load), while `evidenceHash` covers only the business
sections (patient/treatments/invoices/activity) so live-vs-snapshot comparison isn't
defeated by `retrievedAt` changing on every read. Both use a canonical sorted-key
stringify because PostgreSQL jsonb does not preserve key order.

## SnapshotService (`services/crm/snapshot/`)

- `evidence.ts` — pure primitives: `stableStringify`, `contentHash`, `evidenceHash`,
  `validateSnapshotRecord`, `recordCounts`, `compareSnapshotMetadata`,
  `EvidenceValidationError` (`EVIDENCE_INVALID`) / `EvidenceIntegrityError`
  (`EVIDENCE_INTEGRITY`).
- `snapshot-service.ts` — persistence: `createSnapshot` (fetch → validate → seal),
  `loadSnapshot` (validate + verify), `listForSubmission` (newest first; corrupt
  evidence poisons the list loudly by design), plus the pure delegates
  `validateSnapshot` / `compareSnapshotMetadata`.

Retrieval always goes through `getCRMConnector()` — the snapshot engine works
identically over the mock connector today and the Playwright connector once
credentials exist. Nothing imports Playwright; nothing bypasses the seam.

## Developer UI (`/dev/snapshot`)

Super-Admin playground: pick an audit submission → search patients (never
auto-selects among ambiguous candidates) → optional retrieval window → **Retrieve
live CRM** (preview, nothing stored) → **Create snapshot** (sealed + listed) → view
the evidence JSON with full metadata (connector kind, selector version, retrievedAt,
window, format version, hash) → **Compare vs live CRM** (identical/changed badge +
per-section drift lines) → **Export JSON**.

## Tests (22 new; suite 233 across 24 files)

- `evidence.test.ts` (pure): canonical stringify vs key order, hash repeatability,
  provenance-independence of `evidenceHash`, schema rejection with `EVIDENCE_INVALID`,
  comparison outcomes (identical / count drift / field-level edit / demographic change).
- `snapshot-service.integration.test.ts` (local PostgreSQL): create with full
  metadata, DB round-trip, repeatability (same patient → identical evidence hash),
  window persistence + application, **tamper detection** (row edited behind the
  service → `EVIDENCE_INTEGRITY` on load), malformed stored evidence →
  `EVIDENCE_INVALID`, unknown submission/snapshot/patient → `NOT_FOUND` (nothing
  persisted), snapshot-vs-live comparison, newest-first listing.

## What this sprint deliberately did NOT do

No OCR, no AI, no findings, no logbook comparison, no orchestrator wiring, no CRM
synchronization. The orchestrator's `CRM_RETRIEVAL` stage still runs its mock
executor — wiring it to `snapshotService.createSnapshot()` is a one-call integration
reserved for the sprint that connects the full pipeline (documented risk below).

## Risks before OCR integration

1. **Orchestrator wiring is pending** — the pipeline stage and the snapshot engine
   exist but are not yet connected; until then snapshots are created via `/dev/snapshot`
   only.
2. **One audit day = many patients** — the engine handles N snapshots per submission,
   but *which* patients get snapshotted comes from confirmed OCR output; that mapping
   (OCR names → find → disambiguate → snapshot) is exactly the OCR-integration sprint.
3. **Live evidence quality** is still bounded by M0041/M0042's blockers: until the
   service account exists, every snapshot is mock evidence.
4. **Snapshot growth** — full-history records for heavy patients could be large;
   retrieval windows bound this, but the OCR sprint should default to windowed
   captures around the audit date.
