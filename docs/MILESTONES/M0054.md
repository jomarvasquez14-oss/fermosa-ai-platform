# M0054 — Scheduled Audit Pipeline

> Status: **Complete** (2026-07-14) · Branch: `feature/crm-browser-connector`
> A cadence layer over the existing per-submission orchestration (ADR-038):
> schedules declare WHEN, `PipelineRun` records the OUTCOME, and the runner
> walks a **stage list that is data** — with **OCR present but disabled**, ready
> to switch on. Composes the real rule/finding/report/snapshot services; adds no
> second orchestrator.

## What shipped

- **Schema (migration `20260714235613_m0054_scheduled_audit_pipeline`):**
  `AuditSchedule` (cadence `MANUAL|NIGHTLY|WEEKLY|MONTHLY`, enabled, optional
  branch scope, last/next run) and `PipelineRun` (status, trigger, optional
  schedule/submission links via `SetNull`, **per-stage results as JSON**, error,
  timings). New `ScheduleCadence` / `PipelineRunStatus` enums.
- **`services/pipeline/pipeline-stages.ts`** — the ordered stage list as data
  (`OCR`→`SNAPSHOT`→`DATASET`→`RULES`→`FINDINGS`→`REPORT`→`STORE`), OCR
  `enabled: false`.
- **`services/pipeline/audit-pipeline.ts`** — pure runner core: walks the list,
  runs each enabled stage's injected runner, records `{stage, status, ms,
  detail}`, records disabled stages as `skipped`, and **stops loudly at the
  first failure** (no later stage runs; run is `FAILED` with the failing stage +
  message). An enabled stage with no runner is itself a loud failure.
- **`services/pipeline/schedule.ts`** — pure cadence math (`nextRunAt`, `isDue`,
  `dueSchedules`); `MANUAL` is never automatically due.
- **`services/pipeline/pipeline-service.ts`** — persists `PipelineRun`, provides
  `defaultRunners` composing the real services, and `runDueSchedules` /
  `runSubmissionPipeline`.
- **`scripts/run-audit-pipeline.ts`** (`pnpm audit:pipeline`) — cron/CI entry:
  `--now --submission <id>` or `--due`. No daemon.

## OCR is wired-but-off

OCR is stage #1 with `enabled: false`. The runner skips disabled stages and
records them — so the pipeline already runs the full pre-OCR flow, and enabling
OCR later is a flag flip plus one runner, with **no change to the runner loop**
(the whole point of the stage-list-as-data design).

## Composition, not duplication

`defaultRunners` calls the existing services — `createRuleEngine().evaluate()`,
`findingService.createForSubmission()`, `getReport()`,
`snapshotService.listForSubmission()`. The pipeline schedules and records the
audit; it does not reimplement it. The existing `AuditOrchestrator` (AuditJob)
is untouched.

## Pre-OCR honesty

With no confirmed logbook entries yet, the RULES stage evaluates the real engine
over an empty entry set (**0 findings — correct**), and SNAPSHOT/DATASET report
current state rather than fabricating work. The delivered value is the wiring.
