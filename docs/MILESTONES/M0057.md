# M0057 — In-app Browser UI Verification (Errata + Method)

> Status: **Complete** (2026-07-15) · Branch: `feature/crm-browser-connector`
> Corrects a standing misdiagnosis: the app login was believed broken through
> the in-app preview browser (M0053 §Verification), so dashboards / analytics /
> reports were marked "not visually verified." Root-caused to an environment
> paint-throttle — **not** an app defect. Login and all three surfaces are
> confirmed working. No code change; documentation + verification method only.

## The corrected claim

M0053 §Verification stated the live authenticated render was "not captured —
the seeded-account sign-in did not submit through the in-app browser (the known
server-action hydration flakiness from M0044)." **Both halves were wrong:**

- **The app login works** through the in-app browser. Proven by driving the
  real Auth.js credentials flow directly (no compositor needed):
  `GET /api/auth/csrf` → 200 · `POST /api/auth/callback/credentials` →
  `opaqueredirect` (success) · `GET /api/auth/session` → authenticated
  `{ role: "AUDITOR" }`.
- **M0044 documents no such flakiness.** M0044's login issue was the *CRM
  connector's* Playwright login-redirect race (`performLogin` /
  `DashboardPage.waitUntilAuthenticated`) — a different browser entirely — and
  it was fixed and marked ✅. The M0053 citation conflated the two.

## Root cause (environment, not code)

When the Browser (preview) pane is backgrounded behind the chat, its pages
report `document.visibilityState === "hidden"` — even the active / fronted tab
(a freshly created tab is hidden too). Chromium paint-throttles hidden pages,
so the tools that need the compositor stall:

| Tool | On a hidden page |
| --- | --- |
| `computer` (screenshot / click / type) | **times out (~30 s)** |
| `read_page` (accessibility tree) | **returns empty immediately** |
| `get_page_text` (DOM text) | ✅ works |
| `javascript_tool` (in-page JS) | ✅ works |

Evidence it is the throttle and not a hang: the page's own `innerWidth/Height`
is 1280×720 with `readyState: complete`; the network log shows no pending
request; `read_page` returns empty *instantly* (AX tree never built) rather
than timing out. The earlier "sign-in didn't POST" symptom was simply
`computer` failing to drive a throttled form — the POST was never attempted.
(The Playwright CRM connector is unaffected: it launches its own headless
Chromium that isn't subject to pane occlusion, which is why live CRM
validation always worked.)

## How to verify the UI (method)

Recorded reusably in `docs/DEVELOPMENT.md` §Verifying the UI in the in-app
browser. In short:

- **Headless (any time):** `navigate` → `get_page_text` for content +
  `javascript_tool` for computed styles / element state. Seeded logins use
  password `ChangeMe@123` (`admin@`, `auditor@`, `manager@fermosa.local`).
- **Screenshots:** require the user to focus / open the Browser pane (flips
  visibility → `visible` → paint resumes). No tool flips pane-level visibility.

## Remaining caveat

The literal login *form widget* (typing into the fields + clicking **Sign in**)
was not driven end-to-end, because that needs a foregrounded pane. The auth
backend and page hydration are proven; the client `signIn(…, { redirect: false })`
handler is very likely fine but is the one path not yet exercised through the
UI itself.
