# M0058 — Activity-log Windowed-Filter Timeout Fix

> Status: **Complete** (2026-07-15) · Branch: `feature/crm-browser-connector`
> The first defect surfaced by the (M0057-unblocked) real-data platform
> testing: `fetchPatientRecord` **with a date window** failed on the
> activity-log filter. Root-caused by systematic debugging to a slow CRM query
> exceeding the driver's action timeout — **not** a selector/actionability
> issue — and fixed with a per-click timeout override. Live-verified.
> CRM stayed **READ-ONLY** throughout.

## Symptom

`pnpm validate:crm -- --search "Mojica"` →
`fetch-record-windowed FAIL — action on .panel-body .text-right button[type=submit] timed out`.
The **non-windowed** fetch passed; only the windowed path (with `from`/`to`
date filter) failed. The audit always windows activity, so this blocked any
real windowed audit.

## Investigation — evidence, not guesses

Read-only live probing of the activity-log filter established, in order:

1. The Apply button is a **single match, visible, enabled, unobscured, and
   stable** (rect identical across animation frames); no datepicker/overlay
   open. → not a selector, hidden, covered, or animation issue.
2. A `force: true` click (skips *all* Playwright actionability checks) **still
   timed out**. → not actionability.
3. A DOM `element.click()` **submitted the form and navigated**
   (`hasFromParam=true`). → the button and form are genuinely functional.
4. Instrumenting the submit: navigation + results-table load measured at
   **~15.5 s**; the connector's click timed out at the driver's **10 s** default
   action timeout (`setDefaultTimeout(actionTimeoutMs ?? 10_000)`).

**Root cause:** the CRM's *filtered* activity query is slow (~15 s live for a
keyword + date-range window). Playwright's `click()` auto-waits on the
navigation the submit triggers, and the 10 s action default is shorter than the
query — a **spurious timeout on a submit that actually succeeded**. The
non-windowed fetch passed because the keyword-only query returns quickly.

## Fix

- `BrowserDriver.click` gains an optional `ClickOptions { timeoutMs? }`
  (non-breaking driver-seam extension). Playwright passes it as the click
  timeout; the mock records it (no rendering, so no timing).
- `ActivityLogPage.applyFilter` submits the filter and waits for the results
  table with a **navigation-sized budget (30 s)** instead of the 10 s default.

Files: `services/browser/driver/browser-driver.ts`,
`drivers/playwright/playwright-driver.ts`, `drivers/mock/mock-driver.ts`,
`pages/activity-log-page.ts`, `pages/pages.test.ts`.

## Verification

- **Unit:** 358 tests pass, incl. a new guard asserting the Apply click carries
  a `> 10_000` ms timeout. The live-only slow query can't be reproduced in the
  mock, so the guard's job is to prevent silent regression of the fix.
- **Live (read-only):** `pnpm validate:crm -- --search "Mojica"` →
  `fetch-record-windowed PASS (18.0 s) — window applied; activity=1` (real
  filtered data parsed). Rest of the checklist green.
- Full `pnpm release-check` green (typecheck + lint + 358 tests + build).

## Operational note

The activity-log **filtered** query is slow (~15 s for a wide keyword + date
window), so a full **windowed** `fetchPatientRecord` runs ~18 s+. This is a
CRM-side characteristic, not connector overhead; scheduled/windowed audits
should budget for it. Recorded in `docs/CRM_DISCOVERY.md`.

## Contracts

Non-breaking: an optional `ClickOptions` parameter on the driver seam
(ADR-031 / ADR-033). No CRM contract change, no schema change, no new ADR.
CRM remained read-only (the fix only affects how long we wait for a GET
filter submit).
