> The last connector unknowns closed against the LIVE CRM. Invoice detail +
> payments are now parsed (read-only) and `invoiceDetail` is **enabled**; USER
> role semantics are resolved; selectors, session behavior, and performance are
> re-verified in production. Selector version stays **`crm-selectors/v1`**

> mutated.

## Headline finding: invoice detail is embedded, not a page

M0044/M0049 left `invoiceDetail` off because no detail page or row trigger was
found. Live investigation revealed the CRM embeds the **entire invoice detail**
in each list row as a **base64-encoded JSON `data-details` attribute** on the
`<tr>`:

- `payments[]` — `amount_paid`, `date_paid`, `prn` (reference), `payment_type`
  (method), `received_by` ("badge# Name"), `received_by_id`, `remarks`,
  `deleted_at` / `request_for_deletion` (cancellation state), `service_name`.
- `items[]` — services with `service_name`, `description`, `qty`, `price`.
- Plus invoice-level `amount_to_pay`, `amount_paid`, `remaining_balance`,
  `status`/`badge`, `inv_date`, `due_date`, `no_of_months` (installments),
  `terms`.

Reading it is **strictly READ-ONLY**: the data is already in the list DOM.
`InvoiceTab.readInvoiceDetails` reads `locator(rows).attrs("data-details")`,
base64-decodes, and maps to the payment model — **no click, no navigation, no
detail request.** The `data-clickable` cells (which open a JS modal) and the
mutating controls (New Invoice, request_for_deletion) stay in `neverInteract`.

## Contract change (ADR-039, additive + optional)

One field added to the normalized payment: `status?: string`
(`completed | cancellation-requested | cancelled`, derived from
`deleted_at`/`request_for_deletion`). **Optional**, so evidence snapshots sealed
before M0056 still validate on load; the frozen `NormalizedCrmPatientRecord`
(ADR-027) is **extended, never weakened**; no consumer (reports, rules) must
read it. Every other payment field maps to the **existing** schema — no other
contract change.

## Live performance (production, headless)

| Operation | Time |
| --- | --- |
| Login (cold, incl. Chromium launch) | ~7.7 s |
| Patient search (ambiguous, 11 candidates) | ~1.9 s |
| Open patient + treatment/invoice tabs | ~2.4 s |
| Full record (profile + tabs + activity) | ~15.7 s (≈5.6 s on session reuse) |
| **Invoice detail parse (10 invoices)** | **41 ms** |
| Activity log | ~2.7 s |
| Logout (POST form) | ~6.8 s |

**Bottleneck:** the full-record fetch (~15.7 s) is dominated by multi-tab
navigation + politeness delays, not parsing. Enabling invoice detail added
essentially nothing (41 ms) because the detail rides along in the list DOM
rather than requiring a per-invoice fetch.

## Read-only guarantee

Only reads: `login`, tab navigation, `locator.attrs`, `table`, `evaluate` (DOM
capture). No `data-clickable` cell, no invoice/payment action control, no form
submit — verified across the whole live run.

## Known limitations / outstanding unknowns

- Staff **role** is not in the retrieved data (see WS4) — resolving it needs the
  CRM's staff directory, out of scope for the read path.
- "Completed By" was **not observed** in the invoice/payment `data-details`; the
  treatment USER column remains the only staff attribution on treatments (not
  guessed further).
- Live evidence (DOM captures, screenshots) is stored under
  `docs/crm-reference/validation/` — **gitignored, PII, local-only.**

## Verdict

The CRM Browser Connector is **production-ready**: it faithfully reproduces what
an auditor sees — patient, treatments, invoices with full payment history
(including cancellations), and activity — entirely read-only. The only remaining
platform blockers are external: the OCR dataset, an Anthropic API key, and OCR
prompt calibration.
