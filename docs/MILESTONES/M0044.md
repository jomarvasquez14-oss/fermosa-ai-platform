## Method

Supervised live run through `http://localhost:3000/dev/browser` (Super-Admin
cockpit), `CRM_CONNECTOR=playwright`, real read-only session. Evidence sources:
Next dev-server logs, the connector's own results surfaced in the cockpit, and
operator screenshots. No patient PII is recorded in this document (outcomes and
counts only) — the CRM remains the source of truth; the platform only read.

## Live-only defect found and fixed

**Login raced the post-submit redirect.** The session manager checked for the
dashboard the instant the submit click returned — before the live server's
login redirect completed — and reported `CRM_FORBIDDEN` on a login that had in
fact succeeded. Invisible against the mock driver (which flips auth state
synchronously); only a real server exposed it. Fix: `performLogin` now waits for
the dashboard avatar to render (`DashboardPage.waitUntilAuthenticated`, bounded
by the navigation timeout) before deciding. Committed in `a066a3b`. A direct
probe against the live login page (credentials from `.env`, never printed)
confirmed the account authenticates and lands on the dashboard.

## Environment finding (not a connector defect)

Headed Chromium (`CRM_BROWSER_HEADLESS=false`) fails to launch from a
non-interactive session with `spawn UNKNOWN` — a headed browser needs an
interactive desktop to draw its window. Tool-launched dev servers must therefore
use `CRM_BROWSER_HEADLESS=true`; headed observation works only when the dev
server is started from an operator's own terminal. Headless verification is
functionally identical (same navigation, same results) and is what backs the
evidence above.

## Remaining unknowns / blocked

1. **Invoice DETAIL view — BLOCKED (payments stay `null`).** No HTML capture of
   the detail view exists (only the invoice LIST/tab `Fermosa _ Invoice.html`
   and two JPG photos). Per the standing decision, `capabilities.invoiceDetail`
   stays **disabled** until the detail HTML or a live-confirmed trigger is
   provided. Payments parsing is implemented and tested but gated off; retrieval
   is not attempted. Invoice-level `remarks` is deliberately **not** added to
   `NormalizedCrmPatientRecord` (frozen contract, ADR-027 — decision recorded).
2. **Per-field value accuracy** of demographics/treatments/invoices/activity is
   schema-valid but not yet spot-checked field-by-field against the live UI by a
   human. Recommended: open 2–3 patients in the cockpit and eyeball a handful of
   values against the CRM. (No code change expected — this confirms parsing
   fidelity, not structure.)
3. **`performedBy.role`** remains `"unknown"` — the CRM USER-column semantics
   (aesthetician vs encoder) still need one answer from clinic staff.
4. **Live logout + forced inactivity/reconnect** not exercised this session;
   both are contract-tested against the mock. An optional live-logout button on
   `/dev/browser` would let an operator close the loop.

## Verdict

The live CRM connector is **validated for the audit read path**: it logs in,
maintains one read-only session, searches with correct outcome semantics
(including ambiguity), and retrieves schema-valid normalized records across all
page families. The remaining gaps are a blocked capability (invoice detail,
awaiting an artifact) and human spot-checks — not connector defects. This
milestone does not claim more than was observed.
