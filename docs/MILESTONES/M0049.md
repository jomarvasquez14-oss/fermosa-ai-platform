## Method

`pnpm validate:crm -- --search "<common surname>"` runs two layers of checks
sequentially: **seam-level** through the production `getCRMConnector()`
contract (health, search semantics, full-record retrieval, windowing, session
reuse) and **page-level** through a `BrowserManager` (login timing,
fingerprints, screenshots, invoice-detail discovery, logout, recovery). The
probe only READS: the sole state it touches is its own login session — login,
logout and re-login are themselves the recovery paths under validation.
Search terms are passed at run time so no patient name exists in the script.

## Live-only defects found and fixed (the point of this milestone)

1. **`healthCheck` misreported "not logged in" as layout drift.** An
   unauthenticated dashboard visit redirects to `/login` (verified live), whose
   DOM fails the dashboard fingerprint — so a fresh session's health probe
   claimed the selector map was broken. Fix: the probe authenticates first
   (`ensureAuthenticated()`); its job is "can we reach AND log in".
   Test: fresh-session healthCheck in `browser-framework.test.ts`.

2. **The live empty-result phrasing crashed no-match searches.** The
   server-rendered patients list renders `<td colspan="5">No clients
   available</td>` — the old `/no (data|matching)/i` guard missed it and row
   parsing failed loudly on a perfectly normal outcome. Fix: shared
   `isEmptyTableResult` in `utils/parse.ts` — a single-cell row starting with
   the word "No" in a multi-column table is the empty state; the phrasing is
   not load-bearing. Patients + invoice + activity pages now share it.

3. **The activity-log fingerprint was a coin flip.** The Filters panel is
   `.panel.is-collapse` — its inputs exist in the DOM but theme JS decides
   their visibility after load. A visible-wait fingerprint on
   `input[name=from]` passed in the morning (M0044) and failed in the
   afternoon. Fix: the fingerprint anchors on `#activity-logs-table` only, and
   `applyFilter` deterministically expands the panel first (client-side
   `a[data-toggle=panel-collapse]` — no request leaves the browser) when the
   inputs are hidden. The mock driver now simulates the collapsed panel and
   `fill()` gained Playwright-parity (times out on hidden targets) so the
   expansion path is genuinely tested.

4. **A patient with no matching activity crashed retrieval.** The activity
   table's single-cell empty row was parsed as an entry, whose empty `Date`
   failed date parsing. M0044 never saw this — its patient had activity. Fix:
   `readEntries` uses the shared empty-state guard; empty activity is `[]`.

Selector map: still **`crm-selectors/v1`** — the fingerprint change and the
added `filtersToggle` element are non-breaking v1 refinements (same rule as
M0042A); no structural break, no v2, no new ADR.

### Test-harness fix (found while gating M0049)

The full `release-check` surfaced 43 "failing" third-party test files — all
inside a nested git worktree's `node_modules` (a background task's workspace
under `.claude/worktrees/`). Root cause: `vitest.config.ts` had
`exclude: ["node_modules", ".next"]`, which **replaced** vitest's robust
`configDefaults.exclude` (`**/node_modules/**`) with a bare `"node_modules"`
that only matches the top-level directory — so any nested `node_modules`
(worktrees, sub-packages) got globbed for package tests. Fixed by restoring
`configDefaults.exclude` and adding `**/.next/**` + `**/.claude/**`. Not caused
by the connector changes; the stray worktree was left untouched (it belongs to
another task and carries an unmerged commit).

## Note: window semantics are per-section (not a defect)

The windowed run returned **0 treatments but all 10 invoices** for the same
patient and window. This is correct: `inWindow` filters each section on its
own date axis — treatments on `performedAt`, invoices on `dateUpdated`
(last-modified), activity on `occurredAt`. A patient whose treatments predate
2026 but whose invoices were touched in 2026 legitimately shows exactly this
split. Auditors comparing a logbook window to CRM invoices should know the
invoice filter is last-modified, not invoice-created (the CRM invoice list
exposes only DATE UPDATED).

## Known CRM behaviors (learned live)

- Unauthenticated visits to protected pages 302 to `/login`.
- Server-rendered lists use bespoke empty-state phrasings per page
  ("No clients available", DataTables' "No data available in table").
- The activity Filters panel's initial collapse state is decided by theme JS
  after load — DOM presence ≠ visibility on this CRM.
- The invoice list carries no per-row navigation hrefs; its detail view is
  reached by a JS-only control (identity unknown).
- Logout is POST-only with a CSRF token (never a bare GET) — the session
  manager already models this.

## Known CRM limitations (unchanged from M0044)

- Search is NAME/MOBILE server-side only; dob/email refine client-side.
- `performedBy.role` semantics still need one answer from clinic staff.
- Per-field value accuracy remains a human spot-check (schema validity is
  machine-verified; field-by-field eyeballing vs the live UI is not).

## Remaining risks

- **Invoice detail** is the one closed door: payments stay `null` until the
  trigger is identified (capture or operator instruction). Everything else on
  the audit read path is now live-verified end to end.
- Forced **server-side inactivity expiry** was not induced (only the CRM
  controls its session TTL); the recovery path it triggers is the same
  detect-login-page → re-authenticate path validated here via logout.
- The mock driver does not simulate the unauthenticated `/login` redirect;
  healthCheck's live behavior is covered by the live probe instead.
