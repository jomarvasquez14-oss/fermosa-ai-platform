## Objective

Implement persistence for the audit-submission workflow strictly per
[DOMAIN_MODEL.md](../DOMAIN_MODEL.md): create drafts, upload images, save/resume drafts
losslessly, and submit — after which the submission is immutable evidence. No OCR, AI,
CRM, matching, or reports.

## Architecture Decisions (details in ADR-024/025)

- **Drafts persist on first save.** New submissions stage client-side (2A.1 UX intact);
  Save draft/Submit creates the row and uploads each image in its own server action —
  one failure never restarts the batch, and metadata survives as `UPLOAD_FAILED` for
  retry. Stable `LogbookImage` ids are born server-side at registration and never change.
- **Immutability is a service-layer guarantee.** Every mutation passes a guard that
  rejects non-draft states; submit re-checks status inside its transaction, so
  concurrent submits can't double-fire. The UI merely reflects what the service enforces.
- **Security in depth:** `audit:upload` route/page guards; every action re-validates
  input (Zod + the same file rules as the client) and re-derives the actor; the service
  scopes all reads/writes (BM → own branch, Auditor → read-only, SA → full); image
  binaries are served only through an access-checked route handler.
- **Audit trail vs. events:** `AuditTrailEntry` is the durable record (six business
  actions); the in-process bus publishes `submission.submitted` / `logbook.image.stored`
  as notifications (ADR-018 semantics).
- Server-action body limit raised to 12 MB to carry 10 MB images (`next.config.ts`).

## Known Limitations

- A failed upload whose browser `File` handle is gone (draft reopened later) cannot be
  retried client-side — the user removes and re-adds the image. Server metadata is
  preserved either way.
- Local storage backend only; cloud providers are config-selectable but unimplemented
  (throw `NotImplementedError`).
- Integration tests run against the local dev database (isolated throwaway branch/users
  per run, cleaned up after). A dedicated test database lands with CI.
- No pagination on the submission list yet; fine at current volumes.
- Trail records mutations, not reads; read-access logging is a future compliance call.

## Future OCR Integration (Sprint 2B)

The seams OCR plugs into, with nothing to refactor:

1. `submission.submitted` event / `SUBMITTED` status is the trigger point for the
   pipeline (`AuditService.executeStep` — still `NotImplementedError`).
2. Images are fetched via `getStorageProvider().get(storageKey)` and passed to
   `AIProvider.extractLogbook` as `{ storageKey }` refs (interfaces already aligned).
3. Results land on the future `OcrResult` entity (DOMAIN_MODEL.md §3) — never on the
   submission or image rows beyond the denormalized `ocrConfidence`.
4. Status advances `SUBMITTED → OCR_PROCESSING → OCR_REVIEW` per the §5.1 state machine;
   `SubmissionStatusBadge` already renders every state.
