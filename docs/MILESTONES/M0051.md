# M0051 — Pilot Audit Dataset (Audit Packages)

> Status: **Complete** (2026-07-14) · Branch: `feature/crm-browser-connector`
> The first end-to-end audit-dataset workflow: given patient ids or a date
> range, build a **reproducible, self-verifying** on-disk evidence package for
> one branch and audit date — no OCR, no findings yet, just the sealed
> read-only CRM evidence an audit will stand on.

## What an audit package is

`services/audit-package/` composes existing read-only pieces into one bundle:

```
audit-packages/<branch-slug>/<audit-date>/
  <crmId>/
    patient.json  treatments.json  invoice.json  activity-log.json   (business)
    snapshot.json          # full sealed record + contentHash + evidenceHash
    metadata.json          # provenance (connector, selector version, retrievedAt)
  manifest.json            # per-file SHA-256 + per-patient hashes + packageHash
  audit-metadata.json      # who/when/what — VOLATILE provenance
  verification-report.json # re-hash result, written at build time
```

It introduces **no new persistence and no new CRM access path**. It reuses the
connector seam (enumeration, ADR-037), the dataset writer (M0050
`writePatientFiles`), and the snapshot engine's hashing (ADR-035). The
submission-owned DB evidence snapshots (M0043) are **untouched** — this is a
file-based bundle for a pilot workflow, not a second persistence layer.

## Inputs

- **Explicit patients:** `--crm-id` (repeatable). Retrieved directly.
- **Date range:** `--from/--to`. Enumerates the clinic (ADR-037), retrieves each
  patient windowed, and keeps only those with in-window content. Requires an
  enumerable connector — fails loudly otherwise.
- `--branch` (the branch under audit) and `--audit-date` (default: today) scope
  the package directory.

## Reproducibility contract

The package's `packageHash` is a SHA-256 over the **sorted patient
`evidenceHash` values** — and `evidenceHash` (ADR-035) covers the business
sections only, excluding the volatile `retrievedAt`. So the **same CRM data
yields the same `packageHash` across runs and machines**, proven by a test that
builds the same patients into two directories and asserts equal hashes and
equal per-file entries. All volatile provenance (`generatedAt`, per-patient
`retrievedAt`) lives in `audit-metadata.json`, which never feeds `packageHash`.

## Verification

`verifyAuditPackage(packageRoot)` (also run automatically at build time, and via
`pnpm audit:package … --verify`) is a pure filesystem re-hash:

- recomputes every manifest-listed file's SHA-256 and compares,
- re-derives each patient's `evidenceHash` from the stored `snapshot.json`,
- recomputes the `packageHash`,

and reports per-patient issues plus an overall `ok`. Tested against both a
**mutated business file** (SHA-256 mismatch caught) and a **doctored manifest
packageHash** (recomputed hash disagrees). Never contacts the CRM.

## Read-only + failure isolation

Only `listPatients` / `fetchPatientRecord` are called. A per-patient retrieval
failure is recorded in `audit-metadata.json.failures` and the package
continues — the same loud-but-isolated policy as the dataset builder.
